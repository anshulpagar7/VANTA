03 — Data

A world nobody could tune against.

Outcome probabilities were authored before any policy existed, and policy code is forbidden from reading them. That constraint is what makes the numbers worth anything.

The failure taxonomy is Razorpay's own

Razorpay's error object exposes source, step and reason alongside a code and description. VANTA's events are generated on those same three axes, so the simulator speaks the same language as the real API and the vocabulary is not invented.

Ambiguity is the point

The error slug deliberately does not determine the true cause. payment_failed splits across four different root causes; card_declined splits between a hard and a soft decline. The true cause is hidden ground truth that no policy can read.

# world/params.py — frozen before any policy existed
"payment_failed": {
    ISSUER_SOFT_DECLINE: 0.40,
    INSUFFICIENT_FUNDS:  0.30,
    ISSUER_HARD_DECLINE: 0.20,
    TRANSIENT_GATEWAY:   0.10,
}

Without that ambiguity, diagnosis would be a lookup and a language model would have nothing to contribute. With it, diagnosis is a genuine judgement call — and, as the results show, that is precisely where the model earns its place.

How an outcome is decided

Four factors multiply: how recoverable the true cause is at all, how well the chosen action fits that cause, how much the attempt has decayed, and whether the timing is right. Each customer also carries a hidden responsiveness draw that no policy can see — without it, perfect play would exist, and a benchmark where perfect play exists measures nothing.

p = base_recoverability[cause]
  × action_fit[cause][action]
  × attempt_decay(attempt_no)      # 1.00, 0.62, 0.38, 0.22, 0.12
  × timing_multiplier(hours)       # peaks near +24h
  × customer_responsiveness        # hidden

Every arm faces an identical world. Random draws are keyed on (seed, event_id, attempt_no, action) with blake2b, never a shared stream. Policies make different numbers of calls in different orders; a shared stream would hand each arm a different sequence of luck and the comparison would be meaningless. Results are bit-identical across Linux and Windows.

The audit database

Every decision — authorized, blocked, abstained, review-required — is one row. Append-only is enforced by the database itself, not by convention.

CREATE TRIGGER audit_no_update BEFORE UPDATE ON audit
BEGIN SELECT RAISE(ABORT, 'audit log is append-only'); END;
20
columns per decision, including the diagnosed cause, the confidence, the block reason and the world's own probability trace
2
triggers rejecting UPDATE and DELETE, with two tests that try and are refused
144
diagnosis buckets, cached once and committed, so anyone reproduces the model arm with no API key

Development and holdout

Seeds 11–15 were used to build and tune the policies. Seeds 101–105 were never touched until the policies were frozen, committed and tagged. The holdout command refuses to run at all unless that freeze marker exists.

$ vanta evaluate --suite holdout --no-llm
refusing to run holdout: POLICIES_FROZEN marker absent.
Freeze the policies first (ADR-003). One shot, no re-tuning.

One holdout run, by design. Had the numbers disappointed, they would still be the numbers on the next page.
