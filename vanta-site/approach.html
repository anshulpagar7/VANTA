02 — Approach

Separate intelligence from authority.

A language model in a money-moving loop is the central risk. "We prompted it carefully" is not an answer to that. The boundary has to be structural.

Four layers, four packages

A recommendation can never become an executable action directly. It must pass through the policy engine, which is the only holder of the token that mints one. The executor accepts nothing else.

DiagnosisClosed enums, confidence bounded to [0,1], sanitised free text. Describes the world; never acts on it.
RecommendationScores candidate interventions and proposes an authorization request. Still carries no authority.
Policy engine13 deterministic guardrails, then one of four outcomes:
authorized · review required
blocked · abstained
ExecutionAccepts a minted action and nothing else. Simulated for the benchmark; Razorpay test mode for the demo.

Abstention and review-required are outcomes, not failures. Razorpay's own published model holds sensitive actions for merchant approval, so VANTA mirrors that rather than inventing a parallel vocabulary.

The boundary is a test, not a diagram

# execution/types.py — only the policy engine holds this
_POLICY_TOKEN = object()

def _mint(token, **kwargs):
    if token is not _POLICY_TOKEN:
        raise AuthorityError(
            "AuthorizedAction may only be constructed by the policy engine")
    return AuthorizedAction(**kwargs)

Four tests hold this in place: a token-guarded constructor, an executor that rejects anything unminted, a syntax-tree scan proving the diagnosis layer never imports the execution layer, and property-based tests asserting over hundreds of generated customer states that a blocked request never produces an action.

The honest limit. This bounds what the model may do, not how well it reasons. A wrong diagnosis cannot exceed its permissions, but it can still spend a permitted retry on a payment that was never recoverable. That cost is real and it is measured.

Three guardrails go beyond the published set: a per-episode attempt cap, quiet hours with a contact cooldown, and a promise-to-pay suppression window.

Four policies, and why the fourth one exists

ArmDiagnosisDecision logic
A · naivenonefixed retry at +1h, +6h, +24h
B · rule ladderhand-written map from the error codefixed escalation path per cause
B+ · scoring, no modelhand-written mapexpected-recovery-value scoring
C · scoring + modellanguage modelexpected-recovery-value scoring

B+ is the arm that makes the result meaningful. Without it, if C beat B you could not tell whether the win came from the language model or from the better decision arithmetic wrapped around it — and that is the first question a reviewer should ask. B+ and C are literally the same class in the same file, differing only in which function supplies the diagnosis.

A test enforces exactly that: fill the diagnosis cache with the rules-based answers, run arm C, and it must match arm B+ to the rupee. If the two ever diverge for any other reason, the ablation stops meaning anything and the build fails.
